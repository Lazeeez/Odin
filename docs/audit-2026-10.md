# Audit, October 2026

Phase 0 of [PLAN.md](../PLAN.md): does the repository match its README, and what would an outside reviewer trip over? Everything here was checked on 2026-10-13 at commit `540a1d9` plus the fixes listed in section 8.

## 1. Summary

- **The numbers hold.** 267 README numbers were recomputed from result files with no mismatch, and the rows that were re-run reproduced exactly, ranking for ranking.
- **A reviewer could not have checked them.** `results/` was git-ignored, so none of the evidence was in the repository. That is fixed.
- **Five claims in the README are stale, imprecise or untraceable** (section 4), and one ADR states a test-set discipline the logs contradict (section 5).
- **The website failed on large repositories once GitHub's API limit was hit.** That is fixed for sites that run the relay (section 6).

## 4. Claims that are wrong or misleading as written

1. **"Excluding tests is the largest single win at recall@1."** It gains +0.037. Hybrid (+0.079), learning to rank (+0.075) and the cross-encoder (+0.063) each gain more. The sentence was true when only the lexical steps existed.
2. **Denominators.** The headline says "300 issues" but the function row scores 291: the 9 issues whose fix is module-level only are skipped. The retriever table states no denominator. Only the significance table says 291. A reader comparing against a paper that keeps or drops such issues differently will be misled.
3. **hit@k next to recall@k.** The headline table reports hit@10 (79.4%); the sentence under it compares against "30.8% function recall@10 with plain BM25". On the same metric the starting point is 32.6% hit@10, or the end point is 77.2% recall@10.
4. **ADR 0006 shows learned-ranker numbers from the corrupted embedding store** (function recall@10 0.744, MRR 0.485) with no note. The README says they are superseded; the ADR itself does not, unlike ADR 0007.
5. **The parity claim** (837 files) describes a test that is not the one in the repository.

## 5. Test-set discipline

The README says nothing was trained or tuned on Lite and that Lite is run once per final configuration. What the logs show:

- **GPU pipeline.** One Lite run per retriever row, plus `ltr-v1` (the learned ranker on the corrupted store, superseded by ADR 0008). Tuning used Verified minus Lite and full minus Lite, as stated.
- **Distilled reranker.** Validation favoured it at function level (MRR 0.634 vs 0.623). It was then scored on Lite, came out worse, and was not adopted. That is a decision taken on the test set. It went in the conservative direction, and no reported number changed because of it, but the rule was to decide on validation.
- **Browser pipeline before the current ranker.** `depth_check.txt` scores Lite at several rerank depths next to the dev set. `browser_ltr_stage2.txt` and `browser_ltr.txt` are two complete runs with different stage-2 models, both scored on Lite (hit@10 0.698, then 0.701). ADR 0010 says "Lite was then run once".
- **Current browser ranker.** Choices were made by project-grouped cross-validation with rules declared first (ADR 0011). The export was run three times while a batching bug was fixed; only the last printed scores.

[results/test-evals.log](../results/test-evals.log) now lists every evaluation that could be reconstructed: 33 on Lite and 2 on the unseen-project set. New evaluations append a line.

Nothing here suggests a number was chosen because of Lite. The record is still looser than the README claims, and Lite is now a well-used test set. Phases 4 and 5 (fresh issues, other benchmarks) are the real answer.

## 6. The website when GitHub's API limit is hit

Anonymous visitors get 60 GitHub API requests an hour per network. Observed on 2026-10-01 with the limit exhausted:

- **Django:** the file list fell back to jsDelivr and the repository loaded, more slowly.
- **Transformers:** jsDelivr cannot list a repository that large, so the load failed with a clear message naming the limit and its reset time. Nothing crashed.

The site caches a file list for ten minutes, so an ordinary visitor uses one request per repository. Someone loading many repositories in an hour would hit the limit.

**Fixed:** with the relay on, the file list now comes from the archive, and no GitHub API request is made ([ADR 0012](decisions/0012-archive-file-list.md)). Without a relay the behaviour above is unchanged.

Two findings made after the audit:

- **Ties at a cut-off are broken differently in Python and in the browser.** Python's `top_k` keeps an arbitrary subset of units whose scores tie exactly at the cut-off; the browser keeps the lowest indices. It surfaced as two of 46 pinned parity queries and once in the parity test on Odin's own source. Making Python deterministic there could move a published ranking by a tied item, so it is left for the owner to decide.
- **The embedding model's licence is non-commercial.** `jinaai/jina-code-embeddings-0.5b` is CC-BY-NC-4.0. The repository's code is MIT, but the full-pipeline numbers depend on that model ([data/LICENSES.md](../data/LICENSES.md)).
